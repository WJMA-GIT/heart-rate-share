## 二、断连前最后几条有效记录说明了什么

断连（如果真有）之前最后的 BLE 记录是三条 `phase=subscribed`（11:18:51–55），
以及订阅瞬间那条 `HrsFormatException: Empty measurement`。

**日志能证实的：**

1. **没有 GATT 错误码**。0.3.2 既不读 `FlutterBluePlus.logs`，也用 `debug` 级
   才输出逐包日志；日志里唯一的 `[hrs] ERROR` 是一条**空载荷**通知的解析失败
   （`HrsDecoder.decode` ← `FlutterBluePlusSource.connect.<anonymous>` 调用栈
   完整），跟断连无关。所以"133 / 8 / 19 / 22"一类的系统错误码**在这份日志里
   不存在**，不能据此判断是 GATT 层被踢。
2. **App 没有被杀、没有重启**。同一进程同一会话号，09:00:03 只有一次
   `logger initialized`，之后 2 小时 40 分再没有新的初始化行；也没有任何
   `lifecycle` 记录（0.3.2 不记这个）。所以"App 被杀"在本会话内可以**排除**。
3. **11:18:56.602 之后链路仍然活着**。判断依据：`phase=idle` 的 863 条日志后
   面，每条都对应一次 `_emit(_snapshot.copyWith(lastRawBytes: bytes))` ——
   0.3.2 里只有心率通知回调会这样做。也就是说 **notify 流在"断连"之后仍在
   1–2 秒一条地送数据，一直送到日志结束**（22 分钟）。链路没断。
4. **没有任何重连尝试**。11:18:56 之后 `connecting` 一次都没再出现 —— 这与
   代码侧结论（0.3.2 没有自动重连）完全一致。

**日志没覆盖、只能推断的：**

- 那条 `idle` 是**扫描收尾**写进去的，不是 GATT 断开事件。证据是时间差：
  第二次扫描起点 11:18:46.598 → idle 11:18:56.602，差 10.004 s，正好是
  `startScan` 里 `await Future<void>.delayed(timeout=10s)` 的收尾点；而 0.3.2
  的收尾代码是无条件 `_emit(copyWith(phase: idle))`。若真是 GATT 断开，
  通知流不可能紧接着再送 22 分钟。
- 用户"看到"的断连 = 界面「连接状态：空闲」，不是数据真的停了。这点无法从
  0.3.2 日志直接读出（Debug 未开启，没有 BPM/raw 行），但 0.3.4 每次连接后
  补了一条 `code=hrs_first_sample`，下次一眼可辨。
- 心率带型号、手机型号、系统版本、当时是否息屏 —— 日志都不含。

| 断连后状态残留 / 重连白等 2 秒 | **未涉及**（没有重连发生）。仍保留。 |

**新发现的根因（上一轮代码审查漏掉的路径）：**

> **扫描收尾会把已经建立的连接状态覆写成 `idle`。**
> `startScan()` 在 `await Future.delayed(timeout)` 之后无条件 `_emit(idle)`；
> 用户在扫描结束前点「连接」时，10 秒后那一条陈旧的 idle 就把 `subscribed`
> 冲掉。界面显示"空闲"，而链路和心率通知都还在跑。本会话 11:18:56.602 就是它。

## 五、据此落地的修复（0.3.4）

1. **扫描收尾不再写脏 phase**：`scan_tail.dart` 抽出纯函数决定收尾动作 ——
   扫描已被接管（连接流程/新扫描）时什么都不写；链路活着时写回 `subscribed`；
   否则才写 `idle`。传输层用 `_scanEpoch` 版本号判定"是否已被接管"。
2. **服务层再防一道**：扫描期间到达的 `idle` 不视为掉线（等一拍再清标志，
   避开快照异步投递的时序）。
3. **空载荷通知不再刷 ERROR**：0 长度直接丢弃，记 debug
   `code=hrs_empty_notification`。
4. **链路状态可直读**：每次真实状态转变记一条 `link state=connected` /
   `link state=disconnected wasUp=?`（`code=link_connected|link_disconnected`），
   下次日志里"真断"和"误报"一眼可辨。
5. **日志降噪**：`connection phase=` 只在 phase 真正变化时记录 —— 本会话
   863/879 行（98%）是重复 idle，真正的证据被淹没。
6. **数据流自证**：每次连接建立后的第一条心率样本记 info
   `code=hrs_first_sample bpm=…`，一行就能证明"数据在动"，不必开 Debug。

测试：`test/scan_tail_test.dart`（3 项，覆盖本次现场路径）+ `ble_reconnect_test.dart`
新增 2 项（扫描收尾假掉连、phase 未变化不刷日志），全量 38 项通过。

### 6.2 「连接成功 → 断开」到底几秒

同一事件按不同起点算，得到三个数（日志实测）：

| 起点 | 时刻 | → `phase=idle` | 秒数 |
|---|---|---|---|
| 用户点「扫描」 | 11:18:46.598 | 11:18:56.602 | **10.004 s** |
| 用户点「连接」 | 11:18:49.490 | 同上 | **7.112 s** |
| 首次 `subscribed` | 11:18:51.186 | 同上 | **5.416 s** |

**只有 10.004 秒是有机制解释的**：它精确等于 `startScan()` 里
`await Future<void>.delayed(timeout: 10s)` 的收尾点（第一次扫描也吻合：
34.281 → 45.277 = 10.996 s，首次多约 1 秒的平台调用开销）。

用户说的"十几秒"与 5.4 秒有出入，三种可能，都需要新日志判定：

1. 用户报的是"点扫描到看见空闲"的整段（=10 秒，最接近"十几秒"）；
2. 用户习惯在扫描进行中就点连接，但每次点扫描的时机不同，感知被拉长；
3. 确实存在另一条**真的**在 10~20 秒断开的路径（本日志里没发生）。

**注意：这个假空闲只在"扫描还没结束就点连接"时出现。**
如果等扫描自己结束（10 秒）再连接，收尾早已过去，不会出现假空闲 —— 这也解释了
为什么它不是每次都必现。

### 6.3 连接后 10~20 秒窗口内，逐条排查

| 可疑路径 | 核查结论 |
|---|---|
| connected 未稳定就订阅 | 日志：连接请求 → `discovering` 1.65 s，`discovering` → 订阅成功 **43 ms**（服务表来自平台缓存）。没有"未稳定就订阅"的证据，但 43 ms 偏快，下次若出现 `notify_unverified` 就值得追。 |
| notify 订阅超时 | `setNotifyValue` 默认超时 15 s，超时会抛 `FlutterBluePlusException` 并进 `error` 阶段 —— 不会表现为"静默变空闲"。本次订阅 43 ms 成功。 |
| 首包解析异常（RR/佩戴状态）导致订阅被 cancel | **不成立**：解析在 `try/catch` 里，异常只记日志不取消订阅；日志里那条 `Empty measurement` 之后通知仍在继续送达。 |
| 读特征失败后未重试 | 旧版本确实没有重试（失败 → `error` 阶段，等人点）。0.3.3 起有退避重连。 |
| 连接超时参数过短 | 15 s，本次实际 1.65 s 建链，无关。 |
| 定时器误伤 | **命中**：扫描 10 秒收尾定时器。 |
| notify 静默停止 / CCCD 失效（Services Changed 0x2A05） | **旧版本完全没有处理**（没有监听 `device.onServicesReset`，也没有重订阅路径）。本日志里没发生，但这是同量级的真实缺口，见 6.4。 |
| 扫描与连接抢射频 | 旧版本 `connect()` 不 `stopScan()`，用户完全可能在扫描进行中连接。本日志里连接发生在扫描窗口内（46.6→56.6），链路撑住了，但这是已知的稳定性风险。 |

### 6.4 0.3.5 追加的修复

1. **notify 中断自动重订阅**（`lib/ble/notify_recovery_policy.dart`）：
   设备还在但通知停了 → 重新 `discoverServices` + `setNotifyValue` 原地恢复（不重建链路，空窗几十毫秒）；同一 30 秒窗口内超过 2 次才升级为整条重连，避免带子反复重置服务时忙等。
2. **监听 `device.onServicesReset`**：Android Services Changed 会让 CCCD 失效、通知从此静默而链路仍在 —— 以前这种情况会一直显示"已连接"但没数据。现在记 `code=services_reset` 并自动重订阅。
3. **连接前先 `stopScan()`**：消除扫描与连接抢射频；并在扫描撞上进行中的连接时记
   `code=scan_while_connected`，给下一轮日志留证据。
4. 失败路径全部带 `code`：`notify_resubscribe`、`notify_resubscribed`、
   `notify_resubscribe_failed`、`notify_recovery_reconnect`、`services_reset`。

测试：新增 `notify_recovery_policy_test`（4 项，覆盖"设备还在→重订阅 / 设备没了→重连 / 预算用尽→升级重连"），全量 **42 项通过**。
